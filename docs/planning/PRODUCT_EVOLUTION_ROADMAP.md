# 产品演进方向与新功能路线图

日期：2026-09-13。状态：产品提案。执行拆分见 [新功能开发计划](NEW_FEATURE_DEVELOPMENT_PLAN.md)；前置工作见 [稳定性开发计划](V0_1_STABILIZATION_DEVELOPMENT_PLAN.md)。

本路线图基于现有代码、产品规格和本地审查提出产品假设，没有开展市场调研、竞品比较或用户访谈。优先级表示当前建议，不表示市场需求已经得到验证。

## 1. 产品应继续解决什么问题

建议围绕个人深度写作建立优势：用户有一个话题、一些素材或一篇旧稿，系统帮助他找到值得表达的内容、组织读者理解，并以可控制的修改把文章完成。

三项需要由产品实际证明的承诺：

1. **写之前想得更清楚**：知道主张是什么、适用边界在哪里、准备让读者理解什么。
2. **修改时保留已有价值**：能指出具体问题，解释影响，提出局部修改，保留用户已认可的段落。
3. **写完后能使用与回查**：成稿能带走，素材依据能回查，版本和修改决定能够恢复。

优先服务现有 Intent-Rich Writer：叙事分析、观点文章、个人经验表达与短篇场景写作。事实核对、论证与反例功能首先适用于非虚构；小说入口保留其人物与情节约束，不能硬套“论点—证据”的统一评分。

## 2. 功能选择原则

| 原则 | 选择标准 |
|---|---|
| 贴近完成文章 | 能减少卡住、重写或搬运成本，不能只增加可点击界面 |
| 用户仍有决定权 | 角度、事实、修改和整稿替换都能查看并决定 |
| 复用现有资产 | 优先复用 discovery、patch、source、version 和 Workspace |
| 额外成本有理由 | 新增一次模型调用需对应明确的用户收益，并记录延迟 |
| 小范围可验证 | 每项能力先做最短完整流程，失败后可以撤出 |
| 表述有依据 | “检查未完成”“找不到材料依据”“模型推断”不能包装成验证通过 |

## 3. 候选功能与优先级

| 编号 | 候选功能 | 用户收益 | 当前建议 | 主要不确定性 |
|---|---|---|---|---|
| F01 | 本地成稿导出与项目备份 | 文章可带走，项目可恢复 | 第一批；先导出，再独立交付备份恢复 | 常用格式与恢复频率尚未调研 |
| F02 | 写前确认卡 | 在付出正文生成等待前，先确定要表达什么 | 第一批核心功能 | 多一个决策步骤是否减少总重写时间 |
| F03 | 修订工作单与保留片段 | 知道先改哪里，逐条改，不破坏已满意段落 | 第二批核心功能 | 诊断排序与定位是否足够可靠 |
| F04 | 论点与素材依据卡 | 看清关键陈述基于什么，哪些只是推断 | 第二批，先限用户提供的素材 | 模型能否正确判断支持关系 |
| F05 | 读者路径检查 | 找出推进停滞、突跳和过早解释的位置 | 第三批实验 | 是否优于现有 Review，是否值得额外调用 |
| F06 | 本地选题箱 | 保存、筛选、继续已有选题，减少重复生成 | 第三批低风险候选 | 用户是否真的会复用旧选题 |
| F07 | 候选稿对照与选用 | 比较两种写法，保留当前稿再做选择 | 第三批按需求选择 | 额外生成成本与选择负担 |
| F08 | 研究辅助模式 | 对事实密集话题收集可回查材料 | 后续独立范围，先验证资料工作流 | 来源质量、事实时效、成本及工具边界 |
| F09 | 可编辑写作地图 | 调整读者理解顺序，再提出受影响段落的改稿 | 后续独立范围，先验证精确关联 | 结构变化往往超出局部补丁范围 |

F01、F02 的优先理由是：前者补足从工作台到实际使用的出口，后者直接增强已有 Meaning Discovery 的用户价值。F03 和 F04 对应产品最重要的可控修改与素材保真承诺。排序是待验证判断，不能替代真实使用反馈。

## 4. 第一方向：写前想清楚

### F02 写前确认卡

用户流程：输入话题 → 可选“先定角度” → 查看 3–5 个简洁候选 → 选择/修改 → 确认后写作。

卡片只展示用户可理解的成品信息：主张、核心问题、关键机制、适用边界、读者可能获得的认识。避免展示内部推演日志，也不显示没有校准依据的“思想深度 9.2 分”。

默认 Quick Write 继续支持直接写作。确认卡是可选择的控制方式，不强迫所有用户经过新向导。对于明确提供角度的用户，以其角度为主，模型只能提出修正建议。

**验证假设**：减少“写完才发现角度不对”的重写次数，节省总等待时间。记录选择用时、后续重写次数、生成总耗时与最终稿保留情况；不能只看候选点击率。

### F06 本地选题箱

现有话题建议已经能生成并保存在浏览器。本功能新增的是可迁移到项目数据库的收藏、状态、标签和任务关联，不重复建设话题生成器。

最小流程：收藏一条 → 添自己的备注 → 标为待写/已写/归档 → 从条目打开或创建写作任务。跨浏览器可读取同一本地服务中的选题；不扩展成自动选题推送或热点抓取。

**启动信号**：实际使用中反复丢失/找不到选题，或需要把已写文章与选题关联。若用户每次都从新话题开始，优先级下调。

## 5. 第二方向：把修改做得具体而可信

### F03 修订工作单与保留片段

用户流程：检查文章 → 看到少量按影响排序的问题 → 标记保留的措辞/片段 → 选择一个问题 → 看局部补丁 → 接受或跳过。

第一版最多突出三项优先问题，其他问题可展开；每项提供位置、具体影响与修改目标。修订后更新状态并使相关旧诊断过期。先逐项生成提案，不实现无人确认的连续修稿。

保留片段是当前 working revision 上的确切引用与范围。涉及保留片段的改动必须明确报冲突，不能仅把“尽量保留”写进提示词就当作实现了保护。

**验证假设**：用户更容易判断先改哪里，接受后返工更少。指标是完成修订所用时间、接受后撤销/恢复率、非目标文本改动情况，以及人工检查的实际改善。

### F04 论点与素材依据卡

实施状态：Product V0.5 工程实现已完成；真实模型关系判断质量仍待 F04-7 人工评估。

第一版只处理用户已提供的 Source。对正文中的关键可核查陈述，展示关联的素材原句、来源名称和关系：材料支持、推断、待补证据、与材料冲突。

“用户确认关联”与“陈述被外部证实”是不同状态。精确引文能在 Source 中定位，仅说明引用存在；支持关系仍需判断。素材变更或正文改写后，原关联必须过期。

**验证假设**：减少无依据的具体陈述，提高用户定位问题与修补文章的效率。评价要覆盖错误支持关系、遗漏以及用户核查耗时；不能只以关联卡片数量衡量成功。

后续可把已确认条目沉淀为项目事实清单，但必须保留来源、版本和适用范围。此步骤不等于自动记忆或 RAG。

## 6. 第三方向：看清读者如何理解

### F05 读者路径检查

实施状态：Product V0.6 工程实现已完成；固定样例已通过契约门槛，真实模型相对现有 Review 的增量收益仍待 F05-5 评估。

现有 Writing Map 展示的是写作计划，段落映射主要是启发式。新功能分析实际成稿：每一段给读者增加了什么、哪些问题被提出/回答、哪里重复或发生推理跳跃。

两种视图明确命名为“原定路径”和“稿件检查”。模型分析给出正文引用与可验证位置；未定位成功的内容不显示为精确诊断。

用户点击“这里没有推进”后仍进入现有修订提案流程。它是模型对可能阅读效果的分析，不代表真实读者实验。

**继续开发条件**：与现有 Review 的对照中发现更多被用户认可的具体问题，并能导向有效局部修订。若只是换一种文字重述现有评分，应合并回 Review。

### F07 候选稿对照与选用

现有 Versions 已支持历史对照。新功能的差别是：一个新生成方案可以保留为候选，用户尚未选用时不替换当前稿。

第一版由用户分别触发两个方案，支持同一角度的不同表达或不同角度的完整稿件；可查看共同输入和差异，选用后生成明确版本。不要默认每次生成多份以制造成本和选择压力。

**启动信号**：用户经常换角度或重写，但想保留两个方案再判断。评估比较之后的选用率和总用时，不能只统计生成数量。

## 7. 完成与持续使用：F01 导出、备份、恢复

第一段交付纯文本和 Markdown，明确导出当前工作副本还是某个已保存版本。当前工作副本应先完成保存，无法保存时不得把旧稿悄悄导出成“当前稿”。

第二段交付本地备份包与恢复预检：含文章、版本、素材及必要关系，不含模型密钥。恢复先落入独立库或独立目录核验，不直接覆盖当前正在使用的数据。

DOCX/PDF 可根据实际需求再加；发布到外部平台、团队分享和云同步不包含在此功能中。

**验证方式**：导出内容与选择版本逐字对应；备份恢复后关键对象、关系、当前正文一致。观察用户是否真正导出并在工作台之外继续使用文章。

## 8. 中长期候选的启动条件

### F08 研究辅助模式

先验证“用户给来源 → 检查依据 → 完成文章”的价值，再考虑联网获取来源。可能的后续流程：明确研究问题 → 用户触发检索 → 展示来源候选 → 用户选入 Source → 基于这些材料写作 → 引用可回查。

必须先有 F04 的来源与引用契约，以及查询范围、时间范围、调用预算、来源失败处理的独立规格。第一版不承诺穷尽研究，也不输出没有来源支持的自动权威引用。

进入条件：事实密集任务持续因“缺材料”而失败；手动补素材已经能明显改善；联网获取能降低总准备成本。若手工素材工作流本身不可用，暂缓联网。

### F09 可编辑写作地图

先验证 F05 能把实际稿件准确锚定到段落，再让用户改动结构。最小实验只支持调整两个相邻结构单元的顺序，预览受影响范围，然后生成补丁供逐项决定。

结构调整可能牵涉全文的铺垫、指代和结尾，不能把“只动受影响段落”作为未经验证的保证。若局部处理不足，应显示影响范围并要求用户重新选择，而不是静默扩大。

进入条件：用户多次提出“换顺序但保留好段落”的真实需求；锚定质量和局部重写边界可验证；已有版本分支可撤销试验。

## 9. 建议交付批次

| 批次 | 建议内容 | 粗略工作量 | 决策点 |
|---|---|---|---|
| R0 | 现有产品稳定性与验收 | 9–12 人日，另留 2–3 日风险储备 | 已复现关键问题是否关闭？ |
| R1a | F01 纯文本/Markdown 导出 | 1–2 人日 | 用户能否可靠带走成稿？ |
| R1b | F02 写前确认卡 | 3–5 人日 | 是否减少错角度重写？ |
| R1c | F01 备份与恢复 | 2–3 人日 | 数据迁移与恢复演练是否通过？ |
| R2a | F03 修订工作单 | 4–6 人日 | 是否改善修稿效率且保护原文？ |
| R2b | F04 依据卡 | 5–8 人日 | 支持关系是否可信且便于核查？ |
| R3 | F05 / F06 / F07 中选择一个 | 分别约 5–8 / 2–4 / 4–6 人日 | 用户当前最频繁的阻碍是什么？ |
| R4 | F08 / F09 可行性验证 | 每项先投入 2–3 人日 | 是否有足够证据编写正式实现规格？ |

工作量含实现与针对性验收，均为粗估。每批留出使用反馈时间；不要把所有候选累计成必须完成的排期。F01 两段可分别发布，避免恢复功能拖延简单导出的价值。

## 10. 如何验证产品方向

建议先邀请 3–5 名与现有 persona 相符的实际使用者，各自完成一项真实写作任务；若暂时只有项目作者使用，也要记录独立任务的完成过程，不能把单人偏好推广成市场结论。

访谈关注行为：在哪一步停住、哪部分最终保留、何时选择重写、为什么拒绝补丁、是否带走成稿。不要只问“喜欢这个新功能吗”。

共同指标：

- 从输入到得到一份用户愿意保留并导出的稿件所需的总时间。
- 最终完成的任务数，以及失败/放弃所在环节。
- 接受补丁后是否又撤销或大幅重写。
- 无依据陈述和非目标文本改动在人工样本中的发生情况。
- 用户是否在后续写作中再次使用同一流程。

正式对比前固定评价规则与案例，明确分母和缺失数据。质量评审与产品行为分别记录；原有研究实验与新产品试用分别报告。

## 11. 暂不作为主动开发方向

当前证据不足以支持作者风格提取、Pattern Library、微调、复杂多代理架构、自动长篇生成或团队协作。现有仓库也将这些排除在当前范围之外。它们保留为历史研究议题，只有明确的新需求、独立规格和收益验证才进入后续讨论。

路线图的取舍依据是：优先让用户更快形成值得保留的观点和文章，并能安全地修改、回查、带走它。
