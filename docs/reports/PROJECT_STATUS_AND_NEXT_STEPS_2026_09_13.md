## 1. 判断

项目已经形成完整的本地写作工作台，适合继续个人试用与小范围验收。下一阶段应围绕**数据一致性、主流程可靠性、效果验证**收口，再决定是否扩展功能。

目前有三种不同的完成度：

| 维度 | 当前结论 | 证据与限制 |
|---|---|---|
| 功能覆盖 | V0 / V0.1 主流程已实现 | 素材写作、话题写作、旧稿修改共用 Workspace；有 Review、局部 Patch、Versions、Restore、只读 Writing Map |
| 工程可靠性 | 已有较多防护，仍存在关键边界缺口 | 本机 270 项测试通过，但并发接受、部分写入失败、恢复后的结构关联出现可复现问题 |
| 写作效果 | 有真实调用样例，尚缺当前版本的系统评估 | V1.2 尚有 23 对待盲评；9 月新增命题发现与评审不能由旧实验直接证明有效 |
| 交付可复现性 | 本机可用，干净源码环境尚未闭环 | 一个已跟踪测试依赖被忽略的私人 benchmark 文件；未发现已跟踪的 CI 或浏览器自动化套件 |

建议将下一工作批次定义为“V0.1 稳定性与验收收口”。此名称是工作计划，不表示已经启动新产品版本。

## 2. 已有资产与演进方向

- 引擎 `app/`：WIR、正文生成、语言修复、审阅/补丁、硬检查、基准与消融工具齐备。依仓库规则，V1/V1.2 引擎范围保持关闭。
- 产品 `workbench/`：FastAPI + SQLite + 无构建 JavaScript SPA；引擎通过 adapter 接入，当前规模下无需更换技术栈。
- Quick Write：Meaning Discovery、独立命题评审、反例与边界、结构约束、同角度重写/换角度、失败节点复用已经进入实现。

- 核心资产是“发现值得表达的内容 → 组织读者理解 → 保持局部修改可控”。接下来的验证应围绕这条链路。

规格依据：Product V0 `product/00..10`、Quick Write `product/11..20`；后续经用户要求的扩展主要记录在 `QUICK_WRITE_IMPLEMENTATION_REVIEW.md` 的日期附录中。旧报告中“下一里程碑候选”不构成已批准范围。

### 3.2 第一优先级：补丁提交的一致性

位置：`workbench/db.py:120`、`workbench/service.py:884`。

`Database.exec()` 每条 SQL 单独提交。`accept_patch()` 的“读补丁 → 检查当前版本 → 插入版本 → 更新正文 → 标记接受”没有覆盖整个操作的事务或原子条件更新。现有锁只保护单次 SQL。

确定性并发复现让两个调用在读取同一旧正文后继续，两次都接受成功；故障注入则证明 API 报错时也可能已改动正文。现有顺序执行的 double-accept 测试没有覆盖这种交错。

下一步：把接受补丁的校验与持久化纳入同一事务，并检查受影响行数或使用等价的并发控制。检查拒绝/接受交错、恢复、checkpoint、生成提交的同类边界。事务仅覆盖数据库操作，不能跨越模型调用。对 autosave 与接受/恢复的交错补充版本或工作副本冲突检查。

验收：并发接受最多提交一个版本；任何持久化步骤失败均整体回滚；旧请求不得覆盖新正文；冲突以明确错误返回。

### 3.3 第一优先级：版本与角度/结构的关联

位置：`workbench/db.py:53`、`workbench/service.py:835`、`:945`、`:1129`、`:1250`。

`engine_plans` 关联 meaning，但 `versions` 没有明确关联生成它的 plan；恢复只复制正文。审阅与写作地图调用 `_latest_plan(task_id)`，角度摘要读取最新 discovery。因此，“当前正文”与“当前正文对应的结构”会分离。失败后保留的新结构也需要与已经接受的正文区分。

下一步：先在实现评审中确定版本级 lineage 契约与旧数据迁移策略，再补明确关联。区分“可用于失败续跑的最新产物”和“当前稿件对应的产物”；patch/checkpoint 继承其基稿关系，restore 继承被恢复版本的关系。历史记录无法可靠恢复关联时应标记未知，不能猜测后当作精确来源。

验收：A → B → Restore A 后，正文、角度摘要、地图、审阅输入一致；生成 B 失败时，A 的解释信息不被覆盖；续跑仍可复用 B 的已完成节点。

### 3.4 第一优先级：未提交设置改动的回归

位置：`workbench/static/app.js:704`、`:753`。

当前待提交改动用 datalist 同时保存“预设建议”和“端点确认返回的清单”，保存时又把它当作本地模型白名单。清单请求失败后仍保留默认选项，于是手填模型被误拒绝，并被替换成预设值。

下一步：区分清单的来源、请求对应的 Base URL、加载/成功/失败状态；失败时保留手填值。异步响应不能覆盖请求之后的用户编辑；不要仅凭模型名字判断端点能力。新增提示中的动态内容应按文本渲染或统一转义。

验收：请求失败、切换端点、请求中修改模型、手填自定义模型均不会意外改值或误阻止保存；本机服务断开与模型提供方错误分别提示。

### 3.5 交付阻塞：测试依赖未入库数据

`test_load_real_smoke_cases` 直接读取整个仓库已忽略的 `benchmarks/smoke_cases.jsonl`。仅包含已跟踪文件的源码副本已复现 `FileNotFoundError`。所以“本机 270 项通过”目前不能作为干净检出的通过保证。

验收：没有私人素材、密钥、数据库和本机缓存时，干净源码环境可完成常规测试与 mock 启动。

### 3.6 随后处理：长耗时、可观测性和界面回归

- 生成占用状态按固定 300 秒判过期（`service.py:508`），SSE 也有固定 300 秒截止（`api.py:144`）。当前正常 Quick Write 通常至少包含 discovery、judge、architect、writer 四次模型调用，另有修复/重试；固定时间不能充分区分“仍在运行”和“进程已中断”。长任务与重启的实际表现需进一步专项复现。
- 产品 adapter 使用结构化调用返回的数据，但没有完整持久化命题评审 verdict、被否决的尝试、阶段 usage 等信息；评审不可用时按既有设计继续生成，目前主要留日志。应记录通过、否决与未完成检查的区别，同时保留既有降级策略。
- `reviewView()` 直接遍历所有 summary 字段，real adapter 新增的 `decision`、`wq` 会透传到展示层；应白名单选择展示项并转换成产品文案。
- `app.js` 当前 2021 行，`service.py` 1281 行。先补跨模块边界回归，再按编辑保存、生成状态、设置等职责逐步拆分；无需整体重写或引入重型框架。
- 没有已跟踪的浏览器自动化套件。既有报告明确记录最近一次 Chromium 视觉验收未完成，jsdom/接口通过不能证明浏览器交互与布局正确。

## 4. 建议执行顺序

以下为单人顺序开发的粗估，合计约 8–12 个工作日；真实模型评估耗时取决于提供方及人工评审安排。日期不是交付承诺。

| 批次 | 工作 | 依赖 / 预计工作量 | 可验收产物 |
|---|---|---|---|
| A：建立可重复基线 | 更新实现评审；审阅现有未提交修改；修复合成 fixture 与干净测试入口；整理当前规格补充索引 | 0.5–1 日 | 干净检出测试通过，已知问题有明确复现与范围 |
| B：提交安全 | 补丁事务、条件更新、并发接受/拒绝、部分写入失败、autosave 交错 | A；约 2 日 | 故障与并发回归通过，正文与版本/补丁状态原子一致 |
| C：版本语义 | 版本级 plan/meaning 关联、恢复、失败续跑、旧数据迁移 | B；约 1–2 日 | 当前稿件与解释信息一致，历史数据可安全升级 |
| D：主流程可靠性 | 设置清单状态、真实产品级错误文案、长任务状态/重连/进程重启；审阅展示；浏览器回归 | B、C；约 2–3 日 | 三种入口、局部修改、拒绝、接受、恢复、刷新/断线可走通 |
| E：效果与成本验收 | 阶段记录、当前模型固定配置冒烟；小样本产品评估；完成旧盲评结果回收 | 稳定版本；约 2–3 日，人工评审可提前安排 | 可追溯的成功/失败、耗时、接受率与效果比较报告 |

每个批次独立验收与提交。A–D 属于现有 V0/V0.1 的收口；本轮仅制定计划，尚未开始这些修复。

## 5. 效果验证如何做

### 现有研究闭环

先完成 `v1_2_clean` 剩余 23 对盲评并导入，按原有规则合并 17 对自动平局，产出缺失的质量分析报告。评审者身份需要如实记录；既有 `chatgpt` 标记不能当作人工评审。

这批数据回答当时模型和配置下的引擎消融问题。9 月新增的命题评审、提示词和模型配置需要自己的评估，不能直接沿用旧结论。

### 当前产品的小样本验收

先选 12 个固定案例：话题写作、素材写作、旧稿修订各 4 个，覆盖抽象话题、需素材的事实话题、明确用户角度、严格事实/人物约束、反例、局部修订。固定模型、配置与提示词版本，留存失败样本。

记录以下指标：

1. 主流程成功率与失败阶段，失败后已有正文是否保留。
2. 命题可用性、推进是否成立、反例是否处理、结尾是否留下可迁移的认识。
3. 初稿值得保留的比例，用户需要重写多少。
4. 补丁接受情况、事实/意义偏移，以及选区之外的内容是否变化。
5. 首稿总耗时、各阶段耗时、重试次数与可获得的 token 用量。

自动判定用于筛查，不能代替用户评价。12 例只用于发现问题和建立基线；若要判断机制增益，再设计同模型、可比较预算的匿名配对实验，并报告样本限制。
